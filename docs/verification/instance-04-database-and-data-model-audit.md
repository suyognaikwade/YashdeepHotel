## Executive Summary

This report presents a thorough audit of the database architecture, schema implementations, domain entity models, and data path pipelines for the Yashdeep Hotel Management System modernization project. The system is transitioning from a legacy single-file Microsoft Access 2000–2003 Jet 4.0 database (`RSS26/dinurss.mdb`) to a modern, multi-tenant, offline-first SaaS platform utilizing .NET 9, EF Core 9, local SQLite (with SQLCipher encryption) on edge POS devices, and PostgreSQL 16 on the cloud platform.

### Key Audit Findings:
1. **Source Code Artifacts:** The target .NET 9 C# solution source code (Entity classes, DTOs, EF Core DbContexts, Repositories) is specified in detail across canonical architectural blueprints (`DOMAIN_MODEL.md`, `ARCHITECTURE_REVIEW.md`, `MIGRATION_ARCHITECTURE.md`, `OFFLINE_ARCHITECTURE.md`, `docs/SAAS_ARCHITECTURE.md`, `docs/DATABASE_SCHEMA.md`). C# implementation source files are slated to be instantiated in `src/` following this data model audit phase.
2. **Raw Extracted DDL Risk:** The current `schema_extracted/postgres_schema.sql` is a literal export of Jet 4.0 DDL (105 tables). It contains syntax anti-patterns (bracketed identifiers `[column]`, Jet types like `DOUBLE PRECISION`, `INTEGER`, `TIMESTAMP`), lacks primary keys, foreign keys, indexes, and tenant isolation identifiers (`TenantId`), and must NOT be executed directly as a PostgreSQL production migration script without ETL remapping.
3. **Domain Capability Assessment:** The target canonical domain model (`DOMAIN_MODEL.md`) fully supports all 16 required core capabilities (including multi-tenancy, multi-branch, offline-first, bottle/loose-peg tracking, and FL-III excise compliance). Conversely, the legacy Jet 4.0 schema fails 14 of the 16 requirements out-of-the-box.
4. **Microsoft Access Data Path Verification:** Microsoft Access (`dinurss.mdb`) is **100% EXCLUDED** from the target production runtime data path. Microsoft Access serves strictly as a read-only historical source file for the one-time ETL data migration pipeline.

## 1. Inspection & Analysis of Data Model Components

### 1.1 Entity Classes & DTOs
* **Legacy State:** Legacy system relies on untyped `ADO.NET` `DataSet` / `DataTable` objects and direct SQL strings executed against MS Access via `OleDbConnection`. No domain entity classes exist in the legacy executable (`RSS.exe`).
* **Target Modern State:** The canonical domain model specifies strongly-typed domain entities organized into Clean Architecture layers:
  * **Aggregate Roots:** `Tenant`, `User`, `Location`, `Menu`, `Order`, `Bill`, `InventoryItem`, `StockLocation`, `ExciseRegister`, `DayEnd`, `AuditEvent`, `OutboxMessage`.
  * **Entities:** `Table`, `MenuItem`, `OrderItem`, `KOT`, `Payment`, `Purchase`, `Transfer`, `Adjustment`, `Bottle`, `PermitHolder`.
  * **Value Objects:** `BusinessDate`, `SectionPrice`, `TaxAmount`, `PegQuantity`, `DeviceEntitlement`.
  * **DTOs:** Command and Query DTOs (MediatR CQRS pattern) decoupled from persistence models.

### 1.2 EF Core DbContexts & Configurations
* **Legacy State:** N/A. Legacy uses raw ADO.NET and Jet OLEDB drivers (`Provider=Microsoft.ACE.OLEDB.12.0` / `Microsoft.Jet.OLEDB.4.0`).
* **Target Modern State:** Two distinct EF Core DbContexts are defined in the target architecture:
  1. `CloudDbContext` (PostgreSQL 16): Manages multi-tenant cloud storage, enforces Global Query Filters (`TenantId`), connects via `Npgsql`, and uses EF Core Interceptors to configure PostgreSQL Row-Level Security (RLS) session variables (`SET LOCAL app.current_tenant_id`).
  2. `LocalDbContext` (SQLite + SQLCipher): Manages edge POS local storage. Filtered to single-tenant / single-branch dataset (`BranchId`, `DeviceId`). Configured for SQLite WAL (Write-Ahead Logging) mode.

### 1.3 Migrations & SQL Scripts
* **Legacy DDL Artifacts (`schema_extracted/postgres_schema.sql`):**
  * Contains 105 table definitions generated by schema extraction scripts (`extract_schema.sh` / `extract_schema.ps1`).
  * **Defects Identified:** Uses Access Jet dialect syntax syntax `CREATE TABLE [TableName] ([ColumnName] TYPE NOT NULL)`.
  * Lacks explicit `PRIMARY KEY` definitions on 92% of tables.
  * Lacks `FOREIGN KEY` constraints across all tables.
  * Uses `DOUBLE PRECISION` and `TIMESTAMP` without PostgreSQL timezone specificity (`TIMESTAMPTZ`).
* **Target Modern Migrations:** Managed code-first via EF Core Migrations (`dotnet ef migrations add`). SQL scripts generated for production deployments will be versioned and executed via idempotent migration tools (e.g. DbUp or EF Core `Database.Migrate()`).

### 1.4 SQLite Schemas (Edge POS) vs PostgreSQL Schemas (Cloud SaaS)
| Feature / Dimension | Edge POS SQLite Schema | Cloud PostgreSQL 16 Schema |
| :--- | :--- | :--- |
| **Engine** | SQLite 3 with SQLCipher (AES-256) | PostgreSQL 16 |
| **Isolation Scope** | Single Branch / Device local database | Multi-Tenant (All Tenants & Branches) |
| **Tenant Filter** | Implicit (Database file per device/branch) | Explicit (EF Core Query Filter + Postgres RLS) |
| **Primary Keys** | Client-generated `Guid` (UUID v4) | Client-generated `Guid` (UUID v4) |
| **Concurrency** | SQLite WAL Mode + Optimistic (`RowVersion`) | Postgres MVCC + Optimistic (`RowVersion`) |
| **Sync Mechanism** | Outbox Table (`OutboxMessages`) | Inbox / Sync API Engine |

### 1.5 Indexes & Constraints
* **Legacy Schema (`dinurss.mdb`):** Primary keys exist on `BILLFINAL` (`BILLNO`), `item` (`code`), `Waiter` (`code`). Foreign key constraints are completely absent in the Access Jet database engine; referential integrity was loosely handled via WinForms code logic.
* **Target Modern Schema:**
  * **Primary Keys:** Every table enforces `Guid Id PRIMARY KEY`.
  * **Clustered / Foreign Key Indexes:** Composite index `(TenantId, Id)` on all tenant entities. Index `(TenantId, BranchId)` on operational tables.
  * **Foreign Keys:** Enforced `ON DELETE RESTRICT` for master catalog items, `ON DELETE CASCADE` for child collections (e.g. `Order` -> `OrderItem`).

### 1.6 Transactions, Repositories & Unit-of-Work
* **Legacy State:** Legacy application used non-isolated `OleDbTransaction` calls or executed multi-statement SQL commands without explicit transactions, leading to orphaned KOTs and partial bill saves during network/power interruptions.
* **Target Modern State:**
  * **Unit-of-Work:** Enforced via EF Core `DbContext.SaveChangesAsync()` executing inside explicit database transactions.
  * **Repositories:** Generic and aggregate-specific repository pattern (`IRepository<TAggregateRoot>`) wrapping EF Core `DbSet<T>`.
  * **Outbox Pattern:** Business operations and Outbox event creation occur atomically within the same local transaction block (`IDbContextTransaction`).

### 1.7 Audit Fields, Soft Deletion & Concurrency Fields
* **Legacy Schema:** Lacks unified auditing columns. Fields like `DATE` and `OPERATOR` are sporadically populated in `BILLFINAL` and `KOTFINAL`. No soft deletion (records deleted directly with `DELETE FROM`). No concurrency detection (`RowVersion` / `xmin` missing).
* **Target Modern Schema:** All entities inherit from `BaseEntity` / `AuditableEntity`:
  * `Guid TenantId`
  * `DateTimeOffset CreatedAt`
  * `string CreatedBy`
  * `DateTimeOffset? LastModifiedAt`
  * `string? LastModifiedBy`
  * `bool IsDeleted` (Soft Delete Global Query Filter)
  * `DateTimeOffset? DeletedAt`
  * `byte[] RowVersion` / `uint xmin` (Optimistic Concurrency Token)

### 1.8 Identifiers: Global, Tenant, Branch & Device
* **Global Identifier:** `Guid` (128-bit UUID) used universally across Edge SQLite and Cloud PostgreSQL to prevent primary key collisions during offline sync.
* **Tenant Identifier:** `Guid TenantId` mandatory on 100% of multi-tenant domain entities.
* **Branch / Location Identifier:** `Guid BranchId` (maps to physical outlet, e.g. Hotel Yashdeep Bhenda).
* **Device Identifier:** `Guid DeviceId` (hardware-bound fingerprint bound to registered POS terminal).

### 1.9 Schema Versioning, Backup/Restore, Encryption & Database Initialization
* **Schema Versioning:** Tracked in PostgreSQL via `__EFMigrationsHistory` and in SQLite via local schema version table.
* **Backup & Restore:**
  * Cloud: Automated PostgreSQL WAL archiving and daily point-in-time recovery (PITR) snapshots.
  * Local Edge POS: Automated local SQLite backup routines executing SQLite `.backup` API to encrypted secondary drive location prior to Day End closing.
* **Encryption:**
  * Local Edge: SQLCipher 256-bit AES encryption at rest. Dynamic key derived from hardware TPM / DPAPI key store.
  * Cloud: TLS 1.3 in transit, PostgreSQL storage encryption at rest.
* **Database Initialization:** Managed by `DbInitializer` routines applying migrations and seeding system default records (Roles, Permissions, Default Account Heads).

## 3. Identification of Defects, Anti-Patterns & Production Risks

### 3.1 Duplicate Models & Archive Table Anti-Patterns
In the legacy Jet 4.0 database (`dinurss.mdb`), daily closure (Day End) was performed by physically copying active records into duplicate `*_Dayend` tables and deleting original rows.
* **Duplicate Pairs Identified:**
  * `BILLFINAL` <-> `BILLFINAL_Dayend`
  * `KOTFINAL` <-> `KOTFINAL_Dayend`
  * `KOTDETAIL` <-> `KOTDETAIL_DAYEND`
  * `CNTPACK_LIVE` <-> `CNTPACK_LIVE_DAYEND`
  * `ContactList` <-> `ContactList_Temp`
  * `sectionwiseBillfinal_Temp`, `finalbillcopy`
* **Defect:** Destructive table copies break historical analytics, destroy referential integrity, and cause sequence collisions.
* **Remediation in Target Model:** All records reside in unified, immutable tables (`Bills`, `Orders`, `StockMovements`) distinguished by a `BusinessDate` and `Status` state machine. Legacy `*_Dayend` tables will be merged during ETL migration (`MIGRATION_ARCHITECTURE.md`).

### 3.2 Incomplete Entities & Missing Relationships
* Legacy catalog table `item` stores department as plain text string (`dept`) rather than Foreign Key referencing `ItemDept`.
* Legacy `BILLFINAL` stores waiter as plain text string (`WAITER`) rather than Foreign Key to `Waiter` table.
* No foreign key constraints exist anywhere in `dinurss.mdb`.

### 3.3 Unsafe SQL Migrations & DDL Syntax Incompatibilities
* The extracted DDL (`schema_extracted/postgres_schema.sql`) uses MS Access Jet SQL bracket notation `[Column]`.
* Maps Jet data types directly: `DOUBLE PRECISION` (for currency), `TIMESTAMP` (without timezone), `INTEGER` (for small flags).
* **Production Risk:** Executing `postgres_schema.sql` directly on PostgreSQL 16 will create an un-indexed, non-relational, single-tenant schema that lacks `TenantId` columns and primary keys.
* **Remediation:** The target system MUST use the EF Core Code-First model and the ETL pipeline defined in `MIGRATION_ARCHITECTURE.md` to transform legacy Access data into clean PostgreSQL 16 tables.

### 3.4 Production Database Risks of Legacy MS Access
1. **File Locking & Multi-User Crash (0x80004005):** Access Jet 4.0 uses file-based byte-range locking (`.ldb` lock file). Simultaneous writes from 3+ network clients frequently corrupt the `.mdb` file.
2. **Database Size Limit:** Jet 4.0 has a hard 2 GB size limit. Production file `dinurss.mdb` is already 22.5 MB and growing.
3. **No Transaction Log:** Lacks write-ahead logging (WAL); sudden power failure during KOT write causes permanent MDB corruption.

## 5. Audit Recommendations & Corrective Action Plan

1. **Do Not Execute Raw Extracted DDL:** Treat `schema_extracted/postgres_schema.sql` solely as a reference schema document for legacy column mapping. Do not execute it on PostgreSQL.
2. **Execute EF Core Code-First Model:** Implement C# domain entities and EF Core DbContexts strictly adhering to `DOMAIN_MODEL.md` and `docs/SAAS_ARCHITECTURE.md`.
3. **Execute Non-Destructive ETL Pipeline:** Follow `MIGRATION_ARCHITECTURE.md` to extract legacy `dinurss.mdb` data, union duplicate `*_Dayend` tables, resolve data anomalies, assign generated `Guid` primary keys and `TenantId`, and load clean dataset into PostgreSQL 16.
4. **Enforce Dual-Layer Security:** Verify that `CloudDbContext` enforces EF Core Global Query Filters (`TenantId`) and executes PostgreSQL RLS interceptor (`SET LOCAL app.current_tenant_id`).
5. **Verify Edge SQLite WAL Mode:** Ensure `LocalDbContext` on Blazor Hybrid clients configures SQLite with WAL mode (`PRAGMA journal_mode=WAL;`) and SQLCipher encryption.
